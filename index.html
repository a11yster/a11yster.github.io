Building go-task

A small job queue I built to learn Go

Rohit Menon · December 2025 – January 2026

I learn best by building something. So when I wanted to pick up Go, I skipped the tutorials and gave myself one project: a job queue, from scratch, in about two weeks. It's called go-task.

This is how it came together. There are a few diagrams along the way that you can play with.

What's a job queue?

Some work is too slow to do while someone is waiting. Sending an email, resizing a photo, building a report. A job queue lets your app write that work down as a job, drop it in a line, and move on. Separate workers pick jobs off the line and do them in the background.

Here's that idea, running. Each square is a job. Press Add job to make more, or change the number of workers and watch how fast the line clears.

In go-task the line lives in Redis, a fast in-memory database. Adding a job pushes it onto a Redis list. Workers take from the other end, so the oldest job always goes first.

Goroutines and channels

This is where Go won me over. A goroutine is a function that runs alongside everything else. You start one by writing go in front of a call. They're cheap, so you can have thousands. A channel is a pipe that goroutines use to hand things to each other.

The go-task server starts one goroutine that listens to Redis and drops each job into a channel. Then it starts a few worker goroutines that all read from that same channel. Whichever worker is free grabs the next job. That's the whole engine:

work := make(chan []byte)

// one goroutine listens to Redis and feeds the channel
go func() {
    s.consume(ctx, work, s.queue)
    close(work)
}()

// the workers all read from the same channel
for i := 0; i < s.concurrency; i++ {
    go s.process(ctx, work, &wg)
}

The channel has no buffer, so the listener can only hand over a job when a worker is ready to take it. If every worker is busy, the listener just waits. I didn't write any of that waiting logic myself. The channel does it.

When a job fails

Jobs fail. The network blips, an API times out. So every job carries a small record of its life: its status, how many times it's been tried, and the last error. A job moves through five statuses: queued, processing, and then successful, or retrying and back in line, or failed once it's out of tries.

Turn up the chance of failure below and watch jobs retry until they either make it or give up. Each job here gets two retries.

A job can also have a timeout. go-task runs the job in its own goroutine, then waits for whichever comes first: the job finishing, or the clock running out. Go's select turns that race into a few lines:

select {
case <-jctx.Done():
    err = jctx.Err()   // ran out of time
case handlerErr := <-errChan:
    err = handlerErr   // finished, maybe with an error
}

Jobs that wait

Some jobs shouldn't run right now. A reminder for tomorrow, a report at 9am. For these, go-task puts the job in a different Redis structure, a sorted set, using the time it should run as its score. Once a second, a small loop checks for jobs whose time has come and moves them into the normal line.

Click anywhere on the timeline to schedule a job, and watch it drop into the queue when the clock reaches it.

One quirk shows up in the diagram: the loop moves one job per tick, newest first. So if lots of jobs come due at the same moment, they trickle into the line one a second. That's worth fixing.

Repeating jobs, like every morning at 9, are the part I'm still finishing. Each run is meant to schedule the next one when it's done, using the robfig/cron library to read the schedule.

Things I got wrong

Locks. Every worker looks up the list of registered tasks before running a job. I first protected that list with a normal lock, which meant workers had to wait their turn just to read it. Go has a read-write lock that lets any number of readers in at once and only blocks when something is writing. Switching to it was a two-line change.

-   s.mu.Lock()
-   defer s.mu.Unlock()
+   s.mu.RLock()
+   defer s.mu.RUnlock()

A setting I ignored. I added an option to choose how many workers to run, and then kept starting the default number anyway. Easy to miss, easy to fix, and a good reminder to actually try the option I just added.

What I took away

About 950 lines of Go and two weeks later, I have a much better feel for the language. Go makes doing things at the same time feel ordinary: goroutines to run work side by side, channels to pass it around, and select to wait on whichever happens first.

The code is small enough to read in one sitting. If you're learning Go too, have a look on GitHub.
